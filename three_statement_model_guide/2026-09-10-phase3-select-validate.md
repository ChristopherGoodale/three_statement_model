# 2026-09-10 - Phase 3: Selection and Validation

Builds on Phases 1-2. Covers `select_facts.py` and `validate.py`. This phase surfaced more real bugs than any prior one -- worth reading in full if debugging this pipeline later.

## The "Why" (Design Decisions)

**Target periods are anchored on one reference face concept per period type, not "any date seen in a 10-K."** First pass took the N most recent distinct instant dates across *every* fact in the filing. That's wrong: footnote disclosures cite incidental dates (a subsequent-event balance, a quarterly figure in a note) that can be more recent than the real fiscal year-end and crowd it out of the "N most recent" window -- live symptom was the opening balance sheet date silently disappearing, replaced by dates like `2026-02-13` from the DEI cover page. Fixed by deriving instant/duration period-ends from `BS_TOTAL_ASSETS`/`IS_NET_SALES`'s own concepts specifically (guaranteed present, non-dimensional, reported every year) instead of the whole fact universe.

**Beginning/ending balance pairs (CF cash, RE, RNCI) are the same underlying instant fact, not two distinct facts.** `CF_BEGINNING` and `CF_ENDING` (and the EQ roll-forward's beginning/ending rows) share one XBRL concept -- "beginning of FY2025" and "ending of FY2024" are literally the same tagged value, reused across two presentation rows. Selecting both against the same set of instant dates means both series are keyed by *instant date*, not *fiscal year* -- so `CF_BEGINNING`'s value under key `2025-12-28` means "cash at that instant," not "cash at the start of the year ending then." The first pass at `check_cf_cash_continuity`/`check_re_rollforward`/`check_rnci_rollforward` indexed "beginning" by the current period's own end date and got the whole year's activity back as a spurious "diff" instead of ~zero. Fixed by always looking "beginning" up at the *prior* instant.

**A single-child calculation-linkbase "sum" is treated as incomplete, not a real subtotal.** `IS_DILUTED_IN_SHARES`'s only discoverable calc-linkbase child was Basic shares -- diluted also includes a dilutive-securities effect that isn't its own face line, so a naive "formula = basic" would be silently wrong (and it live-tested wrong, off by exactly the dilutive share count each year). Demoted to `kind: fact` whenever a parent has fewer than 2 children rather than trusting any calc-linkbase parent/child pair blindly.

**A known, explained gap was left in the validation report rather than forced to pass.** Two BS subtotal checks (`CHK_SUBTOTAL_BS_TOTAL_LIABILITIES`, `CHK_SUBTOTAL_BS_TOTAL_CURRENT_LIABILITIES`) still show real, small diffs for FY2022/FY2023 only. Root cause, confirmed against companyfacts directly: `AccruedIncomeTaxesCurrent` and `DeferredIncomeTaxLiabilitiesNet` were both real BS face lines in the FY2023 10-K that zeroed out and were *dropped from the face presentation* in later filings -- so discovery, which only examines the anchor (FY2025) filing's structure, never learns they were ever children of those subtotals. The totals themselves are still correctly selected (sourced straight from the as-filed reported value); only the Python-side reconstruction-vs-reported cross-check is short two now-retired line items for the two earliest periods. FY2024 and FY2025 -- the periods this model actually cares about -- tie exactly. Fixing this properly means examining more than one filing's presentation structure during discovery, which is a real scope question for a future phase, not a quick patch; left open for the owner rather than silently forced to zero.

## Core Concepts

- **Recast resolution happens at the fact level, before any line_id mapping.** `resolve_recasts()` groups by `(concept, unit, dimensions, start, end)` -- the raw XBRL fact key -- and only afterward does `select_facts()` map the resolved value onto whichever line_id(s) reference that concept. Keeps "which value is authoritative" and "which sheet line does it belong to" as separate concerns, matching the data contract's `recasts.parquet` (Sec 7.3) vs `historicals.parquet` (Sec 7.2) split.
- **`allow_missing` lines contribute 0 to a subtotal template, but only when actually declared.** `BS_COMMITMENTS_AND_CONTINGENCIES` (a text-only placeholder, never numerically tagged) and the RNCI custom-tag lines (genuinely absent in years with no NCI activity) are the six lines flagged this way post-Gate-2 -- a Phase 3 correction made transparently rather than silently, listed in the Gate 3 report for the owner to revisit.
- **The safe template evaluator.** `eval_template()` substitutes `{LINE_ID}` tokens with `repr(float(value))`, then asserts the resulting string matches `^[0-9eE+\-*/(). \t]*$` before `eval`-ing with an empty builtins dict -- defense in depth even though every template currently comes from our own trusted `discovery.py` output, not external input.

## Implementation Breakdown

- `select_facts.py`: `filter_10k_facts()` (form + duration-window filter), `determine_target_periods()` (the anchored-concept fix above), `resolve_recasts()`, `select_facts()` (per-line_id, ordered-concept-fallback selection with R3 missing-fact enforcement), `run_select()` (orchestrator, writes `data/curated/{historicals,recasts}.parquet`).
- `validate.py`: 11 identity check functions (spec Sec 9.5 items 1-11) plus `render_report()`/`run_validate_and_report()`. Line IDs for the fixed identities (BS totals, CF section totals, EQ roll-forward components) are resolved constants at the top of the file, pinned to this filing's approved config -- would need re-pointing if a future `discover` run against a different filing changes those ids.
- `run.py select`/`validate` wired up; `validate` exits non-zero when any check fails (for scripting), but never raises past a computed report -- the report itself is the Gate 3 deliverable, not a pass/fail gate on its own.
- Live result: 422 curated `(line_id, period)` rows, 0 recasts (no restatements detected across the filings this data draws from), 76 validation check rows with 4 failures -- 1 expected (`CHK_CASH_TIE`, blocked on the still-open `cash_tie` config item) and 3 explained above (all in FY2022/FY2023 only). 72 checks pass clean, including balance-sheet-balances at all 4 dates, cash-flow arithmetic, the cash roll, and every subtotal outside the two affected years.
